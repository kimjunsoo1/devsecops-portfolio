# 보안 스캔 정책

무엇이 PR 을 막고 무엇이 막지 않는지, 그리고 그 기준을 왜 그렇게 정했는지.

## 차단 기준

| 스캐너 | 대상 | 차단 기준 |
|---|---|---|
| gitleaks | 커밋 히스토리 | 발견 시 무조건 차단 |
| Semgrep | 코드 · IaC · 워크플로 | `ERROR` 등급만 차단 |
| Trivy | 의존성 · 시크릿 · IaC 오구성 | `HIGH` · `CRITICAL` 만 차단 |

시크릿만 등급 구분 없이 차단합니다. 유출된 자격증명은 "심각도가 낮은 경우"가 없습니다.

## 심각도는 결정이 아니라 입력이다

스캐너의 등급은 일반적인 맥락을 가정한 값입니다. 수용 여부는 이 프로젝트의
위협 모델과 비용 구조에서 따로 판단합니다.

예를 들어 Trivy 는 "S3 를 고객 관리 KMS 키로 암호화하라"를 `HIGH` 로 매깁니다.
하지만 사이트 원본 버킷에 담기는 것은 전 세계에 공개될 정적 파일이고,
CMK 는 키당 월 $1 에 요청당 과금이 붙습니다. 월 $32 예산에서 기밀성 요구가
없는 데이터에 그 비용을 쓰는 것은 보안 개선이 아니라 예산 낭비입니다.

반대로 Trivy 가 `low` 로 매긴 항목이라도 우리 맥락에서 중요하면 고칩니다.

## 억제는 기한이 있다

수용한 항목은 `.trivyignore.yaml` 에 **사유와 만료일**을 함께 적습니다.
만료일이 지나면 다시 발견 사항으로 올라옵니다. 영구 면제가 아니라
"이 시점에 다시 판단한다"는 약속입니다.

사유를 적을 수 없는 항목은 억제하지 않습니다.

## 기존 지적사항 처리

모듈 1 을 리포트 전용으로 돌린 결과 27건이 나왔습니다. 처음부터 게이트로
걸었다면 아무것도 못 하고 막혔을 겁니다. 전체를 본 뒤 분류했습니다.

- **고침** — SNS 주제 암호화, CloudTrail 버킷 버전 관리
- **수용** — `.trivyignore.yaml` 참조
- **백로그** — `docs/security-backlog.md` 참조. 차단하지 않지만 Security 탭에
  계속 보이게 두어, 해결되지 않았다는 사실이 사라지지 않게 합니다.
- **모듈 3 에서 처리** — 액션 태그 고정 14건

## 새 지적사항

기준선을 만들어 신규만 막는 방식은 쓰지 않았습니다. 프로젝트가 작아서
전수 분류가 가능했고, 분류 과정 자체가 판단의 기록으로 남기 때문입니다.
