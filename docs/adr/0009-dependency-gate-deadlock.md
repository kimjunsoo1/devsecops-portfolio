# 0009. 의존성 게이트 교착은 통합 브랜치로 푼다

- 상태: 채택
- 날짜: 2026-11-03
- 관련: `.github/workflows/security.yml`, `requirements-ci.txt`

## 맥락

3주차에 Trivy 게이트를 켠 뒤 같은 사고를 두 번 겪었습니다.

**1차 (10월).** 2주간 작업하지 않는 사이 npm 의존성에 HIGH 취약점 9건이 새로
공개되었습니다. 게이트는 레포 전체를 보므로 **모든 PR 이 빨개졌습니다** - 그 취약점을
고치는 PR 까지 포함해서입니다. Dependabot PR 도 막혀서 자동 갱신 경로가 함께 멈췄습니다.

**2차 (11월).** 같은 구조가 두 원인으로 동시에 일어났습니다.

| 원인 | 발생 | 성격 |
|---|---|---|
| `undici` HIGH 4건 | 10/26 | 새로 공개된 취약점 |
| `AWS-0011` 유예 만료 | 11/01 | 기한 장치가 설계대로 작동 |

8일간 `main` 의 security 워크플로가 빨간 상태였고, 열려 있던 Dependabot PR 9건이
전부 막혀 있었습니다.

## 문제의 구조

게이트가 **레포 전체**를 보는 것이 원인입니다. 변경 범위만 보면 이 교착은 생기지
않지만, 그러면 "건드리지 않은 곳의 취약점" 을 아무도 보지 않게 됩니다. 전체를 보는
선택은 유지합니다.

그 결과로 생기는 성질은 이렇습니다.

```
게이트가 전체를 본다
  → 어느 PR 이든 레포 전체가 깨끗해야 통과한다
  → 깨진 상태에서는 "깨진 것을 고치는 PR" 도 통과하지 못한다
  → PR 단위로 하나씩 고칠 수 없다
```

## 결정

**한 브랜치에서 막고 있는 것을 모두 고치고, 로컬에서 0건을 먼저 확인한 뒤 올립니다.**

PR 하나가 한 가지 일만 하는 원칙을 이 경우에는 의도적으로 깹니다. 11월 사고에서는
WAF 적용(AWS-0011)과 `undici` 업그레이드(CVE 4건)를 같은 브랜치에 담았습니다. 서로
무관한 변경이지만, 나누면 양쪽 모두 올라가지 못합니다.

커밋은 나눕니다. PR 은 하나여도 커밋 단위로 보면 각 변경의 이유가 분리되어 남습니다.
PR 설명에 "왜 한 PR 인가" 를 적습니다.

### 순서

1. 로컬에서 막는 것을 **전부 나열**합니다. CI 로그에서 룰 ID 와 CVE 번호를 뽑습니다
2. 로컬에서 고치고 **게이트 명령을 그대로 실행**해 `exit=0` 을 확인합니다
3. 그다음 푸시합니다. CI 에서 처음 확인하면 왕복이 길어집니다
4. 머지 후 나머지 PR 을 리베이스해 묵은 체크 결과를 갱신합니다

### 묵은 체크 결과 주의

오래 열려 있던 PR 의 체크는 **생성 당시 상태**로 남아 있습니다. `main` 을 고쳐도
자동으로 다시 돌지 않습니다. 11월 사고에서 `gh pr checks` 가 보여준 실패 중 두 건이
10/26 과 11/01 의 묵은 결과였고, 실제 실패는 하나뿐이었습니다. 런 생성 시각으로
가립니다.

```bash
gh run view <id> --json createdAt,headBranch
```

`@dependabot rebase` 가 듣지 않으면 `@dependabot recreate` 로 처음부터 다시 만듭니다.

## 재발 방지

교착 자체를 없앨 수는 없습니다. 게이트가 전체를 보는 한 성질상 따라옵니다. 빈도를
줄이는 조치를 넣었습니다.

- **스캐너 버전 고정 + 추적.** `requirements-ci.txt` 에 `checkov` 와 `semgrep` 을
  고정하고 Dependabot 이 `pip` 생태계를 보게 했습니다. 스캐너 업데이트로 룰이 늘어
  PR 이 기습 차단되는 경로를 전용 PR 로 바꿉니다. 고정만 하고 추적하지 않으면
  "기습 차단" 을 "조용한 노후화" 로 바꾸는 것일 뿐입니다
- **주간 처리.** Dependabot 을 매주 월요일로 설정했는데 2주 비우면 적체됩니다.
  9건이 쌓인 뒤에는 어느 것이 교착의 원인인지 가리는 데만 시간이 듭니다
- **예정된 스캔.** security 워크플로를 주간 schedule 로 돌립니다. 코드를 바꾸지
  않아도 새 취약점은 계속 나오므로, PR 이 없는 기간에도 상태를 알 수 있습니다

## 받아들인 것

주간 스캔이 교착을 **빨리 알려주지만 막아주지는 않습니다.** 2주 비우면 돌아온 날
첫 작업이 교착 해소가 됩니다. 1인 프로젝트에서 그 비용은 감당 가능하다고 판단했습니다.

여러 사람이 쓰는 레포라면 선택이 달라집니다. 전체 스캔은 schedule 전용으로 돌려
이슈를 만들고, PR 게이트는 변경 범위만 보게 하는 쪽이 맞습니다. 그러면 교착은 사라지고
"건드리지 않은 곳" 의 책임은 사람에게 돌아갑니다. 어느 쪽이든 공짜는 아닙니다.
