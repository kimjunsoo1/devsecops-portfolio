# 0010. 방어를 공격으로 검증한다

- 상태: 채택
- 날짜: 2026-11-12
- 관련: `.github/workflows/oidc-trust-boundary-test.yml`,
  `.github/workflows/deploy-role-boundary-test.yml`, `docs/evidence/week5-*.txt`

## 맥락

1~4주차에 만든 것은 전부 방어다. 계정 가드레일, OIDC, OAC, 게이트 9종, 탐지
알람, WAF. 각 통제를 넣을 때 "동작한다"는 확인했지만, 그 확인은 대부분 **정상
경로가 되는지**를 본 것이다. 배포가 되고, 알람이 울리고, 스캐너가 통과하는지.

통제가 **막아야 할 것을 실제로 막는지**는 다른 질문이다. WAF 를 4주차에 그렇게
검증했다 - 본인 사이트를 공격해 차단 기록을 확인했다. 그 방식을 파이프라인 전체로
넓히는 것이 이 결정이다.

동기가 하나 더 있다. 지금까지의 작업물이 전부 수비다. 취약점진단·모의해킹이
본업인데 공격 관점의 산출물이 없으면 포트폴리오가 한쪽으로 기운다.

## 결정

세 개의 신뢰 경계를 공격해 거부되는지 확인한다. 각 검증은 본인 계정, 본인
리포지토리만 대상으로 하고, **거부가 성공 결과**다.

| 검증 | 공격 가정 | 겨냥한 공격 단계 |
|---|---|---|
| OIDC trust policy | 다른 브랜치 토큰으로 역할 탈취 | 들어오기 |
| S3 OAC + 버킷 정책 | CloudFront 우회 직접 접근 | 돌아가기 |
| 배포 역할 권한 경계 | CI 장악 후 측면이동·권한상승 | 퍼지기 |

### 설계 원칙

**1. 거부가 성공인 테스트는 판정을 뒤집어 작성한다.**
역할 맡기가 실패해야 잡이 성공하도록 만들었다. 그래야 CI 상의 초록이 "통제가
작동한다"를 뜻한다. 통제가 뚫리면(역할을 맡거나 직접 접근이 되면) 잡이 빨개진다.

**2. 대조군이 없으면 거부는 아무것도 증명하지 못한다.**
S3 직접 접근이 403 인 것만으로는 "접근 차단"인지 "버킷이 비어서"인지 모른다.
같은 index.html 이 CloudFront 로는 200 이어야 403 이 차단임이 증명된다. 권한
경계 시험도 d) 대조군(site 버킷 쓰기 성공)이 있어야 "다 막는 과잉 차단"이
아니라 "정당한 것만 통과시키는 정밀한 경계"임이 드러난다.

**3. 가장 중요한 항목을 명시한다.**
권한 경계 시험에서 핵심은 c) 자기 역할에 관리자 정책을 붙이려는 시도다. 이것이
막혀야 공격자가 CI 를 완전히 장악해도 스스로 권한을 넓히지 못하고, 피해가 세
리소스(site 버킷, 그 객체, 배포 1개)에 갇힌다. 이 한 줄이 뚫리면 나머지 경계가
전부 무의미해진다 - 스스로 관리자가 되면 그만이기 때문이다.

### CIS 를 베끼지 않은 것과 같은 결

4주차 탐지 알람에서 CIS 3.2(MFA 없는 콘솔 로그인)를 이 계정 구조에 안 맞아
제외했다. 침투 검증도 체크리스트를 따르지 않는다. 이 파이프라인의 실제 신뢰
경계가 어디인지 보고, 그 경계를 겨냥한다. OIDC 의 immutable sub, OAC 의
SourceArn 조건, 배포 역할의 리소스 제한 - 전부 이 아키텍처에 고유한 것이고,
범용 점검 도구는 "이것이 막는가"를 묻지 않는다.

## 검증 결과

세 검증 모두 PASS. 증적은 `docs/evidence/week5-*.txt`.

- OIDC: ref 만 다른 토큰(test/oidc-boundary)이 거부됨. StringEquals 완전 일치 동작.
- OAC: 직접 GET·리스팅·평문 전부 403, CloudFront 경유만 200.
- 권한 경계: 측면이동·정찰·권한상승 전부 AccessDenied, 대조군만 성공.

## 검증 중에 드러난 것

검증 워크플로를 짜면서 `curl | python3` 를 썼고, Semgrep 의 gha-curl-pipe-shell
게이트가 그것을 막았다. **방어를 검증하는 코드가 방어에 걸린 것이다.**

처음에는 "테스트 코드니 억제하자"고 생각했으나, 로컬에서 어느 파일 어느 룰인지
측정하니 억제할 오탐이 아니라 수정할 실제 안티패턴이었다. 토큰을 파일로 받아
처리하도록 고쳤다. 신뢰 경계를 검증하는 코드가 공급망 안티패턴을 쓰면 앞뒤가
맞지 않는다.

이것이 처리 기준을 준다. 패턴이 정당하게 거기 있어야 하면 억제하고 근거를 쓴다
(예: 권한 상승 시도에 쓰는 와일드카드 IAM 정책 문자열 - 거부를 유도하려고
전달하는 페이로드다). 더 나은 방법이 있으면 고친다. 둘을 가르는 것은
"이 패턴이 여기 있어야 하는가"이지 "테스트 코드인가"가 아니다.

## 남긴 것

두 검증 워크플로를 레포에 남겼다. oidc-trust-boundary-test.yml 은
test/oidc-boundary 브랜치 push 로, deploy-role-boundary-test.yml 은
workflow_dispatch 로만 돈다. 둘 다 일반 PR 이나 push 에 끼어들지 않으므로 main 에
두어도 파이프라인을 방해하지 않는다. trust policy 나 배포 역할 정책을 손볼 때
회귀 테스트로 쓴다 - 경계를 넓히는 변경(도메인 추가로 다른 브랜치 허용 등)이
의도보다 넓게 열리지 않았는지 확인한다.
