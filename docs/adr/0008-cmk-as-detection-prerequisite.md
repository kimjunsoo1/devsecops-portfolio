# 0008. 고객 관리 키(CMK)는 비용 판단이 아니라 탐지 통제의 전제조건이었다

- 상태: 채택
- 날짜: 2026-10-20
- 관련: `terraform/guardrails/kms.tf`, `terraform/guardrails/detection.tf`

## 맥락

1주차에 예산 알림용 SNS 토픽을 만들 때, Trivy AWS-0095(미암호화)를 해소하려고
`kms_master_key_id = "alias/aws/sns"` 를 넣었습니다. AWS 관리형 키는 월 키 요금이
없고, 이 토픽은 한 달에 알림 몇 건만 처리하므로 요청 요금도 사실상 0 입니다.

그러자 Trivy AWS-0136 이 "고객 관리 키가 아니다" 로 잡았습니다. CMK 는 키당 월 $1
이고, 1인 계정에서는 "키 정책으로 로그 접근을 분리한다" 는 CMK 의 실익이 없다고
판단해 기한부 유예로 처리했습니다. 유예 문장에 이렇게 적었습니다.

> 다만 이 선택은 6주차에 어차피 다시 해야 한다 - AWS 관리형 키는 키 정책을
> 수정할 수 없어서 CloudWatch 알람이 이 주제로 발행하지 못한다.

4주차에 탐지 통제를 붙이면서 그 문장이 **지금** 유효해졌습니다.

## 결정

감사와 알림 경로 전용 CMK 를 하나 만들어, CloudTrail 로그·trail 버킷·CloudWatch
로그 그룹·SNS 토픽을 모두 그 키로 덮습니다.

**이 결정의 근거는 비용 대비 보안 수준이 아니라 기능 가능성입니다.**

CloudTrail 을 CloudWatch Logs 로 보내는 목적은 메트릭 필터와 알람을 걸어 루트 계정
사용이나 IAM 정책 변경을 탐지하는 것입니다. 그 알람은 SNS 로 발행해야 하고, 암호화된
토픽에 발행하려면 `cloudwatch.amazonaws.com` 이 해당 KMS 키를 쓸 수 있어야 합니다.
**AWS 관리형 키는 키 정책을 수정할 수 없습니다.** 따라서 `alias/aws/sns` 를 쓰는 한
알람은 ALARM 상태로 바뀌지만 메일이 오지 않습니다.

즉 선택지는 "CMK 에 월 $1 을 쓸 가치가 있는가" 가 아니라 "탐지 통제를 붙일 것인가"
였습니다. 비용 항목으로 분류해 두었던 것이 실은 기능 전제조건이었습니다.

## 키를 하나만 만든 이유

CloudTrail 로그, trail 버킷, CloudTrail 의 CloudWatch 로그 그룹, 알림용 SNS 토픽은
모두 "감사와 알림" 이라는 하나의 신뢰 경계에 속합니다. 키당 월 $1 이므로 쪼갤 실익보다
비용이 큽니다. 키 정책에 `cloudtrail` / `logs.<region>` / `cloudwatch` / `budgets`
서비스 주체를 각각 조건과 함께 넣어 하나로 덮었습니다.

S3 버킷에는 `bucket_key_enabled = true` 를 켰습니다. 객체마다 KMS 를 호출하는 대신
버킷 수준 데이터 키를 재사용하므로 요청 요금이 크게 줄어듭니다. CMK 를 쓰면서도
실제 추가 비용이 월 $1 수준에 머무는 이유입니다.

## 두 관문을 모두 열어야 한다

키 정책만으로는 부족했습니다. 알람이 메일을 보내려면 서로 다른 두 관문을 통과합니다.

```
KMS 키 정책    - CloudWatch 가 이 키로 암호화해도 되는가
SNS 토픽 정책  - CloudWatch 가 이 토픽에 발행해도 되는가
```

하나만 있으면 알람은 ALARM 으로 바뀌는데 메일이 오지 않습니다. 상태만 보면 정상처럼
보이므로 **가장 찾기 어려운 종류의 고장**입니다.

토픽 정책에도 KMS 와 같은 잠금 위험이 있습니다. 토픽 정책을 설정하면 AWS 기본 정책을
대체하므로, 계정 소유자 문장을 빼면 접근이 좁아집니다. KMS 키 정책은 더 심합니다 -
계정 주체에게 `kms:*` 를 주는 문장이 없으면 키가 잠기고 복구 경로가 없습니다
(`bypass_policy_lockout_safety_check = false` 가 그런 정책을 애초에 거부하는 이유).

## 검증 방법

탐지와 알림을 **따로** 시험했습니다. 한 번에 시험하면 실패했을 때 어느 경로인지
알 수 없습니다.

| 경로 | 방법 | 결과 |
|---|---|---|
| 알림 | `aws cloudwatch set-alarm-state` 로 강제 전환 | 메일 수신 |
| 탐지 | IAM 정책 생성·삭제 | 메트릭 Sum=2.0, 알람 이력 OK→ALARM→OK, 메일 수신 |

CloudTrail 과 버킷 암호화 전환도 단계를 쪼개 적용했습니다. CloudTrail 의
`kms_key_id` 와 버킷 기본 암호화는 EncryptionContext 가 서로 달라
(`aws:cloudtrail:arn` vs `aws:s3:arn`), 한 번에 바꾸면 깨졌을 때 원인이 섞입니다.
각 단계마다 `get-trail-status` 의 `LatestDeliveryTime` 이 **전진했는지**를 확인했습니다.
`LatestDeliveryError` 가 비어 있는 것만으로는 판정할 수 없습니다 - 배달이 완전히
멈춰도 과거 성공 기록은 그대로 남아 오류가 없는 것처럼 보입니다.
