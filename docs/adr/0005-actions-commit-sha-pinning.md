# ADR 0005 — GitHub Actions 를 커밋 SHA 로 고정한다

- 상태: 채택
- 날짜: 2026-09-10

## 맥락

3주차 모듈 1 에서 Semgrep 이 27건 중 14건을 같은 규칙으로 잡았다:
`github-actions-mutable-action-tag`. 워크플로가 액션을 `@v4`, `@v6` 같은
**태그**로 참조하고 있다는 지적이다.

태그는 포인터일 뿐이라 옮길 수 있다. 액션 리포지토리를 장악한 공격자가
`v4` 태그를 자기 커밋으로 옮기면, 그 액션을 쓰는 모든 워크플로가
다음 실행부터 그 코드를 돌린다. 우리 워크플로는 `id-token: write` 로
AWS 역할을 assume 하므로, 그 시점에 공격자는 우리 AWS 계정 안에 들어온다.

2025년 `tj-actions/changed-files` 사건이 정확히 이 경로였다.
태그가 옮겨졌고, 그 액션을 쓰던 수만 개 리포지토리의 CI 로그에
시크릿이 덤프됐다.

## 결정

`.github/workflows/` 의 모든 액션 참조를 40자 커밋 SHA 로 고정한다.
원래 버전은 뒤에 주석으로 남긴다.

```yaml
uses: actions/checkout@08c6903cd8c0fde910a37f88322edcfb5dd907a8 # v4
```

고정 작업은 `scripts/pin-actions.py` 로 자동화했다. 손으로 SHA 를 찾아
붙여넣는 방식은 새 워크플로가 생길 때마다 빠뜨리게 된다.

동시에 Dependabot 을 `github-actions` 생태계에 붙인다.
고정만 하고 방치하면 "옮길 수 없는 태그" 대신 "낡은 코드"라는 다른 문제가
생기기 때문이다. Dependabot 은 주석의 버전을 읽어서 SHA 와 주석을 함께
올리는 PR 을 연다. 고정과 자동 갱신은 반대가 아니라 한 쌍이다.

## 고려한 대안

- **신뢰하는 퍼블리셔만 태그로 쓰기** — `actions/*` 는 GitHub 공식이니
  괜찮다는 논리. 하지만 위 사건도 널리 쓰이던 액션이었고,
  "누가 신뢰할 만한가"를 매번 판단하는 것보다 전부 고정하는 편이 싸다.
- **액션을 리포지토리에 벤더링** — 가장 안전하지만 유지보수 비용이 크고,
  결국 업데이트를 손으로 해야 한다.

## 결과

- Semgrep 지적 14건이 사라진다.
- 액션 업데이트가 자동에서 **리뷰가 붙는 PR** 로 바뀐다. 느려지지만,
  CI 에 들어오는 코드 변경이 눈에 보이게 된다.
- Dependabot PR 도 우리 게이트(gitleaks · Semgrep · Trivy)를 통과해야
  머지된다. 자동 업데이트가 검사를 우회하지 않는다.
